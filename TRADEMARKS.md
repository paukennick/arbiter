# Arbiter trademark policy

"Arbiter" is the name of this static-analysis and repository-evaluation
software, published at `github.com/paukennick/arbiter` and as the Python
package `arbiter-eval`. Nicholas J Pauken ("the owner") uses **Arbiter™** as
a trademark for this software. The mark is not registered; the ™ symbol
signals that the name is used as a trademark, and this project does not use
®.

The name "Arbiter" is also used by other, unrelated software and products.
This policy concerns only the name as it identifies this software and claims
nothing about anyone else's use of it.

The aim, as in the Apache Software Foundation's trademark policy this one
follows, is simple: anyone should be able to tell whether something is the
genuine Arbiter from this project, and whether this project stands behind it.

## Uses that need no permission

You may, without asking:

- **Refer to Arbiter factually**: in articles, talks, documentation,
  comparisons, academic work, issue trackers and package metadata, provided
  what you say is accurate.
- **Say what your work does with it**: "works with Arbiter", "compatible
  with Arbiter", "an Arbiter rule pack", "based on Arbiter",
  "uses Arbiter to scan pull requests".
- **Report Arbiter's output accurately**: "scanned with Arbiter 0.1.0 on
  2026-10-23; no critical findings". Say which version and profile produced
  it, and do not present a scan result as a certification
  ([DISCLAIMER.md](DISCLAIMER.md)).
- **Redistribute unmodified copies** under the name Arbiter, keeping
  `LICENSE` and `NOTICE` as the licence requires. Packaging changes needed to
  install it on a platform, and backported security fixes, still count as
  unmodified for this purpose, provided you say they were made.
- **Keep the name in code**: Arbiter's own identifiers (the `arbiter` command,
  the `arbiter` Python package, `arbiter.yaml`, rule ids such as
  `arbiter/secrets.aws-access-key`) may stay as they are in a fork; renaming
  them is not required.

## Forks and modified versions must be renamed

Forks are welcome; Apache-2.0 allows them. If you **distribute** a modified
version, give it a name of its own that is not confusingly similar to
Arbiter, and describe the relationship accurately.

- Good: "Acme Scanner, based on Arbiter", "a fork of Arbiter with Acme's
  rules".
- Avoid: "Arbiter Pro", "Arbiter Enterprise", "Arbiter for Acme",
  "Arbiter-NG", or a name that differs from Arbiter only by a prefix, suffix
  or spelling.

A private modification you do not distribute needs no new name.

## No implied endorsement

Do not state or imply that the owner or the Arbiter project endorses,
sponsors, certifies, audits, maintains or supports your product, service,
fork, training or results unless that is agreed in writing. In particular:

- Do not describe code, a product or an organisation as "Arbiter certified",
  "Arbiter approved" or "Arbiter compliant", or use a badge or seal that
  suggests the project vouches for it. A badge that links to your own scan
  report and says only that you run Arbiter is fine.
- Arbiter's `verified` precision tier is a property of a finding inside a
  report. Do not use the word to suggest the project has verified your code.

## Package names, domains, accounts and hosted services

Ask first before you:

- publish a package, container image, extension, GitHub Action or
  marketplace listing named `arbiter-eval`, or named "Arbiter" or
  `arbiter-*` in a way that suggests it is the official release or comes from
  this project;
- register a domain name, social-media account or organisation name that
  suggests it is Arbiter's official home;
- offer a hosted service or SaaS under a name built on Arbiter, such as
  "Arbiter Cloud" or "Hosted Arbiter".

Without permission you may say a service is "powered by Arbiter" or "uses
Arbiter", in ordinary text and in a way that makes clear the service is
yours, not this project's.

## Asking for permission

Open an issue on the GitHub repository titled "Trademark permission
request", saying what you want to name and how it will be used. If the
request is confidential, ask in the issue for a private contact, or use
[OWNER CONTACT FOR TRADEMARK REQUESTS: to be provided by the owner].
Permission is given in writing and may be withdrawn if the use stops matching
what was agreed.

## Changes to this policy

The owner may update this policy; the version in the repository's `main`
branch is the current one. A use that was allowed when you began remains
allowed for material already published under it.

# OmniEngineering Trademark And Identity Policy

> **In this repository.** This section is the OmniEngineering identity
> policy, carried with the OmniEngineering workspace that Arbiter includes, and
> it governs the OmniEngineering and OmniContext names only. "Project owner"
> below means the OmniEngineering project owner. The name Arbiter is covered by
> the [Arbiter trademark policy](#arbiter-trademark-policy) above.

This policy protects the project identity while keeping the code, docs,
templates, diagrams, and workspace structure broadly reusable under the Apache
License, Version 2.0.

This is a project policy, not legal advice.

## Protected Project Identity

The protected project identity includes:

- `OmniEngineering`
- `OmniContext`
- OmniEngineering logos, marks, banners, and visual identity assets
- Confusingly similar names or marks used to present a fork, derivative,
  package, hosted service, marketplace listing, extension, or distribution as
  the original project

## Allowed Uses

You may:

- Use OmniEngineering privately, commercially, internally, academically, or in
  public projects.
- Fork and modify the source under the Apache License, Version 2.0.
- Say that your project is "built with OmniEngineering," "based on
  OmniEngineering," or "compatible with OmniEngineering."
- Include attribution required by `LICENSE` and `NOTICE`.
- Use the OmniEngineering name in factual references, documentation, package
  metadata, compatibility notes, academic discussion, or contribution history.

## Uses That Need Permission

You need written permission from the project owner before you:

- Use OmniEngineering or OmniContext as the primary name of a modified fork,
  competing distribution, hosted service, plugin marketplace package, commercial
  product, training product, or consulting package.
- Use project logos, marks, banners, or trade dress as the main identity for a
  modified or independently distributed product.
- Register domains, social handles, package names, trademarks, app listings, or
  organization names that imply official project ownership or endorsement.
- Present modified behavior as the official OmniEngineering release.

## Fork Naming

Forks are welcome. If you distribute a modified fork, use a distinct name and
make the relationship clear.

Good examples:

- `Acme Engineering Workspace, based on OmniEngineering`
- `OmniEngineering-compatible workflow pack for Acme`
- `Fork of OmniEngineering with Acme-specific rules`

Avoid examples:

- `OmniEngineering Pro`
- `Official OmniEngineering Cloud`
- `OmniContext Enterprise`
- Any name or branding that makes users think the fork is the original project
  or officially endorsed.

## No False Endorsement

Do not state or imply that the project owner endorses, sponsors, maintains,
certifies, audits, supports, or warranties your fork, service, product, or
training material unless that relationship is documented in writing.

## Attribution

When distributing a fork or derivative, keep the `LICENSE` and `NOTICE` files
required by Apache-2.0. If you make substantial changes, clearly describe those
changes in your fork's documentation.

## Upstream Contributions

You are not required to contribute changes back. You are strongly encouraged to
return generally useful improvements, bug fixes, diagrams, playbooks, checks,
templates, and compatibility notes to the main project so the wider engineering
community benefits.
